# Demo 1 architecture

User-confirmed scope: this Mac, two RGB USB cameras on a cap, local processing with replaceable modules, and an indoor supervised demo.

## Data flow

```text
Front USB camera ─┐                         ┌─ text-conditioned item detector
                  ├─ latest JPEG ─ Python ─┤
Feet USB camera ──┘   + capture attitude/time     └─ indoor metric monocular depth
                                                    │
AirPods motion ─ automatic reference ─ current attitude      │ NDJSON scene
                              │                     ▼
Local speech ─ wake grammar ─ target query ─ guidance engine
                                                │
                                  target + nearest in-path hazard
                                                │
                              mono pulse voices → HRTFHQ → AirPods
```

`SeearCore` contains geometry, command parsing, freshness checks, approximate target continuity, camera-forward corridor filtering, voice pause/resume and priority. It is independent of AppKit, cameras, ML and audio. `Camera` captures both USB devices using AVFoundation. `VisionWorker` sends one frame at a time over private process pipes and alternates feeds; old frames are replaced, not queued. `vision/backend.py` owns detector/depth inference; `vision/geometry.py` turns depth into observations. A different local or future cloud backend can implement `infer(image, target)` and retain the scene contract. No cloud inference or remote fallback is enabled.

The Python worker loads cached model weights only, refuses remote model code, and uses safetensors. The setup script downloads public weights and packages once. Images/audio are not recorded or uploaded. Python diagnostics go to ignored `build/vision.log`; no frame or voice-transcript logging is implemented.

## Coordinate and freshness contract

`+X` is right, `+Y` up, and `-Z` forward. Bearings are degrees clockwise from an arbitrary automatically initialized motion origin; that origin is not a walking direction. An observation's bearing is relative to the gravity-level capture heading, after mount and dynamic head-tilt compensation. The front and feet camera optical axes must be aligned in yaw with the cap's forward direction. Their different downward mount angles are entered separately. FOV assumes a rectilinear, square-pixel camera; strongly distorted/wide-angle video requires rectification before use.

Each sample's presentation timestamp is converted from the capture session's synchronization clock to the host's monotonic clock. Camera frames retain that time through inference; driver-delayed buffers do not receive a new time on delivery. Full AirPods quaternion attitude is interpolated using shortest-path SLERP at each capture timestamp; missing or stalled motion history rejects the frame. Headphone axes (+X right, +Y forward, +Z up) are converted to audio axes (+X right, +Y up, −Z forward). The first motion sample establishes only an arbitrary yaw origin: initial pitch and roll remain gravity-relative, so startup does not require a perfectly level head. Projection applies the fixed mount first, then capture tilt with yaw removed. The guidance engine adds capture yaw once, while the HRTF listener uses the complete current forward/up vectors once. Quaternions/vector orientation avoid Euler gimbal lock. The item waveform’s direction-dependent visibility/sharpness also uses the complete head-relative source vector, rather than yaw alone. At an almost vertical forward axis (horizontal norm ≤0.05), the previous horizontal heading is retained; the full 3D rotation is still applied. Pitch/roll never reset the reference or gate inference. After a motion gap over 0.5 s, the next sample starts a new reference generation; old frames, motion history and in-flight scenes from before that generation are discarded. Timestamp interpolation retains the 0.15 s maximum internal gap and 0.08 s endpoint tolerance. macOS environmental automatic listener tracking is disabled to avoid double compensation.

The cap must remain rigidly mounted and aligned with the headphone/head frame; entered mount angles are relative to a level head. AirPods do not measure camera slippage or provide exact surveyed tilt. Physical checks must confirm nod/roll signs and sound alignment. See Apple's [headphone axes](https://developer.apple.com/documentation/coremotion/cmheadphonemotionmanager) and [attitude representations](https://developer.apple.com/documentation/coremotion/cmattitude).

An independent experimental mapper estimates translation and partial room geometry for saved memory/debugging; see [room mapping](ROOM_MAPPING.md). Audio does not consume this map pose. The sound source's range/position is refreshed from the latest camera estimate. Between frames, head rotation is compensated but walking translation is not. This limitation matters near an object and when latency increases.

Both feeds must have estimated depth coverage ≥60% and capture age ≤1.5 seconds, and AirPods updates must be fresher than 0.5 seconds. Invalid numbers, older responses, worker failures and missing feeds cannot produce a valid directional scene. Faults mute directional cues and announce unavailable guidance. These are engineering cutoffs, not a guarantee of timely or correct obstacle detection.

The forward alert corridor is centred on **current head/cap-camera yaw**. For every candidate, the engine computes `wrap(camera_relative_bearing + capture_yaw - current_yaw)` and checks the existing 1.1 m corridor width and forward half-plane in that frame. Audible warnings additionally require estimated horizontal range ≤0.50 m. Fresh images after a turn therefore define the new forward automatically. An older obstacle does not move into the new forward merely because it used to be centred. There is no walking-heading variable, 50° turn gate, Set forward command or direction-reset button.

This implements head-forward monitoring, not body-heading estimation. A sideways glance can leave the actual travel path outside the two cap cameras' coverage. AirPods and cap cameras alone do not establish walking intent. Tilt alone does not pause inference or cues. Looking up, down or sideways can still leave hazards outside both cameras; continuing processing does not establish that unseen space is clear. Audio translation compensation and route planning remain outside this change.

## Estimated geometry and item continuity

Camera FOV, mount pitch, height above floor and a multiplicative depth scale are editable per feed. Defaults are placeholders to replace with measured/calibrated values. The depth model predicts optical-axis depth; pinhole projection, mount pitch and capture-time head tilt yield estimated floor-relative points. The same transform is used by the near-body footwear filter. On the background feet classification schedule, the detector also queries shoes/legs even in neutral mode, sharing that detector image pass with an active item query. Per-query scores/NMS keep these queries separate from item selection. RGB foreground masks constrained to detected near-body footwear and adjacent lower legs are excluded only from occupancy; missing/uncertain masks retain the pixels. See [footwear filtering](FOOTWEAR_FILTER.md).

Tile-supported occupancy above 0.12 m and below 2.2 m provides class-independent obstacle candidates. This avoids making safety alerts depend solely on a limited set of object labels. It does not establish walkability or detect holes, stairs, transparent surfaces, moving hazards or all thin objects.

An item's box samples its central depth region, avoiding a few background pixels. `ItemConfidencePolicy` defaults to the user-selected minimum x=0.50 and relative switching margin y=0.10. At acquisition, the engine picks the highest-scoring valid query match **strictly above x** across both fresh feeds. The worker still proposes boxes above its internal 0.15 score floor; the tracked box samples current-frame depth, and class-independent obstacle occupancy remains independent of item classification.

Production association uses the same feed and persistent visual track ID. Legacy/nontracking backends retain bearing/range association and box overlap when full camera attitude changes by less than 5°. The best eligible challenger can replace the lock only if its score is **strictly greater than the current associated score plus y**, and its capture time is at least that of the current observation. This is a relative margin, not fixed x+y. A 0.70 current match therefore needs a challenger above 0.80; equality does not switch. A 1e−6 score tolerance avoids roundoff-triggered switches at the boundary. Acquiring or switching also requires a score above x and valid geometry.

If an associated match drops to x or below, it produces neither an item cue nor a selected box. Its measured score can still update the internal comparison reference; a later challenger must pass both the floor and margin. If the current item is missing entirely, its last observed score is the comparison reference and no old cue is replayed. A last score plus y at or above 1 prevents automatic switching until a lower current score is observed or Find starts a new selection; the margin is not silently clipped.

Only one selected item is exposed to the debug view, including while an urgent obstacle mutes its audio. Other candidate boxes stay internal for association. Brief stale/tracking faults preserve the lock; pause/resume clears old scenes while retaining it. A full backend/motion-reference reset invalidates the lock and requires another voice Find command before acquisition. Find again explicitly starts a new selection. The backend's Min x and Switch +y fields apply before starting a run and are disabled while running. Settings validation requires x≥0.15, y≥0, and x+y<1; these are session setup values, with defaults restored at app launch.

This is approximate association, not a persistent visual identity guarantee through occlusion or a calibrated probability of correctness. A high-scoring false positive can still be selected (B5). “My backpack” identifies a category; it does not establish ownership. No automatic arrival or physical reach confirmation is inferred from RGB estimates.

The item retains the prototype's broadband/440 Hz single pulse. Hazards use a sharper broadband 1200/1800 Hz double beep with a separate quiet/emergency gain policy, capped at four double-beep cycles per second. Both pass through mono point sources and HRTFHQ. Only emergency-range obstacles suppress the item; soft warnings do not duck it.

Cancel search returns to obstacle monitoring. Voice starts automatically with backend startup and requires the wake phrase and a completed utterance. On-device speech or microphone setup failures are spoken, with no network fallback; the manual Find field is a supervisor debug override, not the wearer’s fallback interface. Cancellation stops item search, not obstacle monitoring. Voice pause mutes directional guidance and suspends new inference requests while keeping the microphone active. Resume retains the search query and item lock, clears old scenes and requires fresh camera results. The supervisor’s Stop backend control stops both cameras, worker and directional audio; voice remains available for a spoken restart using the configured devices. Disable voice is a separate debug override that stops microphone capture.

## Validation boundary

Automated checks cover timing, priority, coordinate signs, command parsing, depth geometry, pipe integration, actual HRTF rendering and signed app construction. Synthetic depth and fixture detections verify software behavior only. A real cached-model inference smoke check establishes that the ML path runs; it does not establish white-cane detection accuracy or real-world navigation performance. Hardware acceptance requires the actual cap, both cameras, AirPods and supervised obstacle/item trials.

## B1/B7/B8: fast tracking and quiet warnings

The GPU was already active (`mps`, Apple Metal). Previously one serial request ran depth **and** OWLv2 on every frame; at about 450 ms each, two-feed freshness repeatedly approached the 1.5 s limit. Production now uses separate `estimate_depth` and `detect` backend methods. Depth, geometry and image-feature tracking return current scenes without waiting for the detector. A single background classifier holds only the latest pending image per feed, runs at most once per second per feed, and shares the existing cached GPU models. Depth and detection use different model instances; each enters its own thread-local inference context. The GPU remains shared, so contention still affects latency. CPU room segmentation is capped at two submissions per second and retains its one-frame mailbox.

Track IDs come from current image evidence, using forward/backward Lucas–Kanade features, RANSAC partial affine motion and a normalized appearance check. Delayed detection boxes are advanced through bounded capture history before use. A classifier match refreshes the score/time of an existing track without snapping its box back to the new detector rectangle. The first lock waits for both initial camera classification scans, comparing the highest eligible score before acquisition. The native engine associates explicit track IDs, retaining the score floor x=0.50 and relative switching margin y=0.10. A repeated Find creates a new search token; old in-flight item results cannot acquire that search. Low-texture objects, occlusion, unsupported motion or a >1.0 s image gap can lose a track. A fresh classification can recover a recently lost identity only with strong matching appearance (patch correlation or geometrically consistent ORB features); a label match alone cannot recover it. This is still approximate visual identity, not personal ownership or a guarantee against drift.

Tracked observations carry the last **real classifier** timestamp and score, separately from image capture time and tracking quality. Optical flow never invents a new class score. Classification older than 2.5 s expires independently of depth freshness; a classifier delay/failure can silence item guidance while current obstacle processing continues. Camera/depth capture age still has the unchanged 1.5 s limit. The native sender rejects duplicate capture times, and images are never relabelled as fresh. Debug text reports depth time, tracking/searching mode and classification age.

User-selected obstacle policy: **silent beyond 0.50 m**, a soft pair of 45 ms taps no more than once every three seconds at 0.20–0.50 m, and stronger 70 ms double beeps at ≤0.20 m (2–4 cycles/s, increasing toward 0.10 m). A three-second soft-warning cooldown survives cue loss/re-entry, so flickering candidates cannot retrigger frequent taps; emergency transitions remain immediate. The warning repeats are sparse, with fixed note lengths rather than stretched notes at slow rates. Soft warnings require matching support in two distinct frames within 0.6 s; repeated evaluation of one frame cannot confirm a hazard. Emergency-range support is immediate. All raw occupancy candidates remain available in scene data; suppressing distant sound does not establish that no obstacle exists.

Only emergency-range cues suppress the item's audio. A soft warning leaves the item at full level. Hazard gain is separately capped and does not use the item's inverse-distance curve. Mono sources and full-attitude HRTF remain in use. RGB estimated horizontal range cannot establish an exact 10–20 cm physical clearance, and temporal support does not prove a repeated depth error is a real obstacle.
